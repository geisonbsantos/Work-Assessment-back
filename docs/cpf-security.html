Melhoria de Segurança — CPF

Data: 2026-06-02
Autor: alterações aplicadas no branch feat/Encrypt_CPF

Resumo

O CPF deixou de ser mantido e pesquisado como texto simples. Agora:

  • O valor do CPF é armazenado encriptado at-rest usando o cast encrypted do Laravel.
  • Foi adicionado um campo cpf_hash (SHA-256) para buscas/validações sem expor o CPF cru.
  • A API passa a mascarar o CPF retornado em responses.
  • Logs e mensagens deixaram de gravar o CPF em texto claro; usam identificadores como id.

Arquivos alterados

  • Model: app/Models/User.php — adiciona cast encrypted e setter que gera cpf_hash.
  • Migração: database/migrations/2026_06_02_000001_add_cpf_hash_to_users_table.php — cria cpf_hash, encripta valores existentes e atualiza dados.
  • Service: app/Services/UserService.php — busca por cpf_hash no login e remove CPF cru de logs.
  • Resource: app/Http/Resources/UserResource.php — máscara do CPF nas respostas da API.
  • Requests: app/Http/Requests/StoreUpdateUserFormRequest.php e app/Http/Requests/ReportErrorFormRequest.php — geram e validam cpf_hash para unique/exists.

Migração e execução (passos)

  1. Garanta backup do banco antes de rodar em produção.
  2. Em ambiente de desenvolvimento com Docker (exemplo): 
    docker compose exec php bash
php artisan migrate
  3. Se usar sqlite (testes locais), a migração ajustou o campo para nullable para evitar erro de adição de coluna NOT NULL.

Rollback

Para reverter a migração:

php artisan migrate:rollback --step=1

Observação: o down() da migração tenta restaurar a constraint única no campo cpf, mas é recomendável testar o rollback em staging antes de produção.

Considerações de segurança

  • As encriptações utilizam as chaves do Laravel (APP_KEY). Planeje políticas de rotação de chave com cuidado — rotacionar a APP_KEY sem strategy de re-encrypt pode tornar os dados inacessíveis.
  • O cpf_hash é determinístico (SHA-256) e permite busca; isso é suficiente para funções de lookup, mas não substitui controles de acesso e auditoria.
  • Evite expor o CPF completo em logs, emails ou templates HTML. A notificação de relatório de erro foi ajustada para mostrar CPF mascarado quando enviada.
  • Restrinja quem pode ler campos encriptados: usuários com privilégios financeiros ou de suporte precisam de aprovação e registro de acesso.

Impactos e limitações

  • Não é possível pesquisar diretamente por CPF em índices sem primeiro fazer o hash — pesquise usando o mesmo algoritmo (remover não dígitos + SHA-256).
  • Consultas que antes usavam where('cpf', $value) foram alteradas para where('cpf_hash', hash('sha256', $cpf)).
  • Operações de full-text ou filtros que esperavam CPF no formato original deverão ser revisadas.

Testes recomendados

  1. Rodar suíte de testes automatizados.
  2. Adicionar testes que verifiquem:
    • Cadastro cria cpf_hash corretamente e armazena CPF encriptado.
    • Login funciona quando busca por CPF fornecido (pré-processado).
    • APIs retornam CPF mascarado.

Checklist pós-migração

  • Verificar integridade dos dados (ex.: contagem de usuários e hashes gerados).
  • Testar fluxos de login, reset de senha e relatórios que usam CPF.
  • Confirmar que logs não contêm CPFs em texto claro.
